# 골든타임

**흩어진 산재 조사 자료와 과거 판정례를 찾아 대조하는 업무를 돕는 도구입니다.** 실무자 인터뷰에서 반복되는 자료 검토를 병목으로 확인하고, 질병군 후보·유사 판정서·사실관계 타임라인을 한 흐름으로 연결했습니다. 현재 구현은 Python 표준 라이브러리를 사용하는 규칙 기반 분류와 정보 검색입니다.

[데모 열기](https://goldentime.onrender.com) · [검색 평가](docs/EVALUATION.md) · [평가 집계 JSON](evaluation/known-item-summary.json)

`Python` · `Public Data API` · `Information Retrieval` · `Vanilla JavaScript` · `Human-in-the-loop`

무료 호스팅 특성상 첫 접속에는 시간이 더 걸릴 수 있습니다.

## 문제를 좁히고 구현한 과정

처음에는 산재 판정을 AI로 보조하는 방향을 검토했습니다. 실무자 이야기를 듣고 나서는 흩어진 서류와 판정례를 반복해서 찾고 대조하는 일을 먼저 풀기로 했습니다. 최종 판단은 조사자에게 두고, 판단에 필요한 자료와 출처를 확인하기 쉽게 만드는 데 집중했습니다.

외부 모델을 연결하기 전에 규칙과 검색만으로 해결할 수 있는 범위를 확인했습니다. 질병군 후보와 매칭 요소를 보여주고, 직력·의료기록의 시점을 대조하도록 구성했습니다. 폐쇄망으로의 이식 가능성을 고려해 웹 프레임워크나 추가 패키지 없이 실행되는 Python API와 화면을 만들었습니다.

## 담당 역할

울산대학교 융합캡스톤디자인에서 **5인 팀장·PM·개발**을 맡았습니다. 현업 인터뷰와 문제 재정의부터 사용자 흐름, Python API, 프론트엔드, 공공 API 연동, 검색·평가 코드와 배포까지 연결했습니다.

팀에서는 아이디어를 기능 목록으로만 나열하지 않고, 조사자가 자료를 찾고 대조하는 순서를 기준으로 요구사항과 데모를 맞췄습니다. “검색이 잘 된다”는 표현을 Known-item Retrieval로, “질병을 어느 정도 찾는다”는 표현을 Top-k 평가로 바꾸어 같은 기준으로 결과를 검토할 수 있게 했습니다.

## 빠른 시작

Python 3가 필요하며 외부 라이브러리 설치는 필요하지 않습니다. API 키가 없으면 저장된 추출 DB 또는 내장 데모 데이터로 흐름을 확인할 수 있습니다.

```bash
python3 app.py
# → http://localhost:8000
```

실제 공공 판정서를 조회하려면 [공공데이터포털](https://www.data.go.kr/data/15110836/openapi.do)에서 서비스키를 발급받아 실행합니다.

```bash
# 맥 / 리눅스
SERVICE_KEY="발급받은_서비스키" python3 app.py

# 윈도우 CMD
set SERVICE_KEY=발급받은_서비스키
python app.py

# → http://localhost:8000
```

### 규칙 기반 분류와 근거 검색

현재 시스템은 질병군과 비교 요소를 규칙으로 추출하고, 요소 일치도를 기준으로 판정서를 검색합니다. 새 판정서를 조회해 원문과 매칭 이유를 보여주므로 결과에서 출처로 돌아갈 수 있습니다. 자료 검색·대조 흐름을 구현하고 평가하는 데 필요한 구성을 택했습니다.

현재 질의 흐름은 규칙 기반 검색과 템플릿 안내로 구성됩니다. 별도 추출 DB를 읽는 경로에는 과거 LLM으로 정리한 데이터가 포함될 수 있습니다. 검색 문서를 바탕으로 초안을 생성하는 단계는 향후 온프레미스 LLM 확장 계획에 두었습니다.

### 실행 환경과 확장

Python 표준 라이브러리만으로 서버와 API 처리를 구현했습니다. 폐쇄망으로 옮길 때는 공공 API 데이터 소스를 내부 DB 어댑터로 바꾸어야 합니다. 현재 공개 데모가 폐쇄망에 납품되거나 운영됐다는 의미는 아닙니다.

```text
STEP 0 (현재)  규칙 기반 분류·요소 일치 검색   외부 패키지 없이 실행
STEP 1         임베딩 유사도                  로컬 한국어 임베딩 검토
STEP 2         NL2SQL                        내부 DB 자연어 질의 검토
STEP 3         온프레미스 LLM                문맥 이해·초안 생성 검토
```

로컬 임베딩은 데이터의 외부 전송을 줄이기 위한 선택지입니다. 도입 시 저장·접근 정책도 함께 검토하며, 모든 단계에서 최종 판단은 조사자에게 둡니다.

### 분류 후보 기록과 사후 대조

분류 후보를 타임스탬프와 해시로 기록하고, 자문의사가 선택한 분류와 나중에 대조하도록 설계했습니다. 일치는 기록에 남기고 불일치는 재해조사 쟁점으로 확인합니다. 먼저 제시된 후보가 판단에 미치는 영향을 줄이려는 설계이며, 인지 편향 감소 효과를 측정한 결과는 아닙니다. 로컬 타임스탬프와 해시는 기록의 변경 확인에 사용합니다.

`law_mapper.py`의 `confidence`는 매칭 신호 수로 계산하는 규칙 일치 점수입니다. 보정된 정답 확률과는 구분합니다.

### 질병군 분류: 1,253건

판정서의 신청내용 서술만 입력해 별표3 질병군 후보를 맞히는지 측정했습니다. 판정 이유는 입력하지 않았습니다.

| 질병군 | 표본 | Top-3 | Top-1 |
| --- | ---: | ---: | ---: |
| 근골격(비척추) | 200 | **98%** | 66% |
| 근골격(척추) | 200 | **88%** | 88% |
| 호흡기 | 200 | **86%** | 79% |
| 난청 | 142 | **89%** | 70% |
| 뇌혈관 | 200 | 74% | 60% |
| 직업성 암 | 200 | 62% | 27% |
| 간질환 | 111 | 36% | 22% |
| **전체** | **1,253** | **79%** | **61%** |

근골격·호흡기·난청의 Top-3는 86~98%였지만, 직업성 암은 62%, 간질환은 36%였습니다. 암→호흡기 82건, 간→뇌혈관 41건의 혼동이 나타났습니다. 진술에 섞인 “폐·과로” 키워드가 우선 매칭되는 규칙 기반 접근의 한계로 보고, 의미 유사도 방식에서 개선 가능한지 확인할 과제로 남겼습니다.

### Known-item Retrieval: 140질의

실제 판정서를 정답으로 두고 부위·부담요인·직종만으로 검색해 원본이 상위에 돌아오는지 측정했습니다. 각 질의는 원본을 포함한 후보 120건에서 평가했습니다.

| 표본 | Hit@1 | Hit@3 | Hit@10 | MRR |
| ---: | ---: | ---: | ---: | ---: |
| 140건 | 37.1% | 65.7% | **77.9%** | **0.521** |

이 결과는 요약 시 Hit@10 78%, MRR 0.52로 반올림할 수 있습니다. 질병군별 Hit@10은 0~100%로 편차가 컸습니다. 평균만으로 검색 품질을 결론내리지 않고 [검색 평가 문서](docs/EVALUATION.md)에 계산 방식과 실패 사례를, [고정 JSON](evaluation/known-item-summary.json)에 집계값을 남겼습니다.

```bash
python3 verify_known_item.py "발급받은_서비스키"
# → 검증결과_요약.txt · 검증기록_사례별.csv
```
