# 골든타임

산재 처리 기간을 줄이라는 문제를 처음 접했을 때, 저는 판정 모델부터 만들기보다 **어디에서 담당자의 시간이 반복적으로 소모되는지**를 먼저 보았습니다.

업무상질병 요양급여신청의 1차 재해조사에서는 진술서·전산직력·의료기록·작업환경 자료의 형식과 출처가 서로 다릅니다. 담당자는 이 자료를 수작업으로 교차 대조하고, 과거 판정서에서 비슷한 사례와 적용 근거를 다시 찾아야 합니다. 병목은 결론을 만드는 계산보다, 판단 전에 필요한 자료와 근거를 빠짐없이 구성하는 과정에 있다고 정의했습니다.

골든타임은 흩어진 산재 자료를 한 화면에서 대조하고 실제 판정서의 유사 사례와 근거를 찾는 **1차 재해조사 보조 도구**입니다. 인정·불인정 판정은 하지 않습니다. 판정은 판정위원회의 권한이며, 도구는 담당자의 검토 범위와 근거 추적을 지원합니다.

**Live demo** · https://goldentime.onrender.com (무료 호스팅, 첫 접속 시 최대 50초)

## 배경

업무상 질병 산재는 인정까지 평균 228일이 걸린다(2024년 신청 173,603건). 병목은 판정위원회 상정 전 **1차 재해조사** — 담당자가 출처가 제각각인 자료를 수작업으로 교차 대조하는 단계다.

이 프로젝트는 "AI로 산재를 판정한다"가 아니라 **"1차 재해조사의 자료 검토를 보조한다"** 로 범위를 좁혔다.

## 문제를 기능으로 번역한 과정

| 업무에서 확인한 문제 | 구현한 기능 | 확인 기준 |
| --- | --- | --- |
| 서로 다른 서류의 시점과 사실관계를 수작업으로 대조 | 직력·의료기록 통합 타임라인 | 날짜 충돌과 비어 있는 근거를 화면에서 확인 가능한가 |
| 유사 판정서를 찾기 위해 긴 본문을 반복 탐색 | 질병군 분류와 요소 기반 유사 판정서 검색 | 정답 판정서가 검색 상위에 재현되는가 |
| 모델이 결론을 먼저 제시하면 담당자 판단에 선입견 발생 | 사전 예측 기록 후 사후 대조 | 예측과 자문의 판단을 독립적으로 비교할 수 있는가 |
| 행정 근거를 추적할 수 없는 생성 결과 | 판정서 원문과 매칭 요소 동시 제시 | 결과에서 출처 문서로 돌아갈 수 있는가 |
| 폐쇄망에서 외부 패키지·클라우드 모델 사용이 어려움 | Python 표준 라이브러리 기반 실행 | 새 환경에서 `python app.py`로 실행 가능한가 |

## 설계 결정

### RAG (검색 기반) — 파인튜닝 아님

판정서로 파인튜닝하면 모델이 인정/불인정 예측을 학습하게 되는데, 이는 판정위 권한을 침범한다. 또한 행정 업무는 근거 추적이 필수인데 파인튜닝 모델은 블랙박스라 "왜"를 답할 수 없다. RAG는 실제 판정서 원문을 근거로 가리키며, 새 판정서를 재학습 없이 즉시 반영한다.

| | 파인튜닝 | RAG (채택) |
|---|---|---|
| 판정 | 예측 학습 → 권한 침범 | 사례 제시, 판정 안 함 |
| 근거 | 블랙박스 | 원문 추적 가능 |
| 갱신 | 재학습 필요 | 즉시 반영 |
| 폐쇄망 | 학습 인프라 필요 | 즉시 실행 |

### 외부 의존성 없음

공단은 폐쇄망 환경이다. 프레임워크·서드파티 패키지 없이 Python 표준 라이브러리만으로 구현했다. `python app.py` 한 줄로 실행되고, 이식 시 의존성 충돌이 없다.

### 단계적 고도화 설계

검증되지 않은 ML보다 투명한 규칙기반으로 시작하되, 인프라 여건에 따라 확장할 수 있도록 설계했다.

```
STEP 0 (현재)  규칙기반 RAG      외부 의존성 없이 폐쇄망에서 운용
STEP 1         임베딩 유사도      로컬 한국어 임베딩, 개인정보 외부 유출 없음
STEP 2         NL2SQL           공단 내부 DB 자연어 질의
STEP 3         온프레미스 LLM     문맥 이해·초안 생성 (판정은 여전히 안 함)
```

### 신뢰성: 사전 예측 → 사후 대조

AI 예측이 담당자·자문의사 판단에 선입견(anchoring)을 주지 않도록, 예측을 자문의사 판단 전에 타임스탬프로 독립 기록하고 사후 대조한다. 일치는 근거로, 불일치는 재해조사 쟁점으로 처리한다.

## 구조

```
dashboard.html   프론트엔드 (단일 HTML, Vanilla JS, SVG 트리·타임라인)
    │ HTTP/JSON
app.py           http.server 기반 API 서버
    ├─ law_mapper.py       별표3 규칙 기반 질병분류
    ├─ (rank_similar)      요소 일치도 기반 유사 판정서 검색
    ├─ timeline.py         직력·의료기록 사실관계 대조
    └─ (guideline)         사업장 조회·자문 의뢰·처리기한
    │
jbpjeong_source.py  질병판정서 API 연동 (요양 필터·최신순·본문 추출)
    │
근로복지공단 질병판정서 조회 API (공공데이터포털)

verify_known_item.py  IR 정량 검증 스크립트 (Known-item Retrieval)
```

파이프라인: 분류 매핑 → 사전 예측 기록 → 유사 판정서 검색 → 사실관계 대조 → 근거 산출

## 담당 범위와 협업

- 산재 처리 기간이라는 넓은 주제를 1차 재해조사의 자료 검토 문제로 구체화
- 업무 흐름과 사용자 피드백을 기능, 데이터 항목과 화면 순서로 변환
- AI의 권한을 판정이 아닌 검색·대조·근거 제시로 제한
- 프론트엔드, 백엔드, 공공 API 연동, 검색 로직과 평가 코드 구현
- 팀의 아이디어와 기술 제약을 하나의 사용자 흐름으로 정리하고 데모·발표 기준을 조율
- 정량 결과가 낮은 질병군과 규칙 기반 접근의 실패 조건까지 문서화

협업에서 맡은 핵심 역할은 현업의 표현, 개발 가능한 요구사항과 검증 가능한 기준 사이를 연결하는 것이었습니다. “검색이 잘 된다”는 표현을 `Known-item Retrieval`로, “질병을 어느 정도 찾는다”는 표현을 1,253건 Top-k 평가로 바꾸어 팀이 같은 결과를 기준으로 논의할 수 있게 했습니다.

## 구현 노트

- **API 정렬 우회** — 조회 API에 정렬 옵션이 없어 최신 판정서가 앞에 오지 않는다. 전체 건수로 마지막 페이지를 계산해 역순 수집 후 접수번호로 재정렬했다.
- **요양 건 필터** — API에 급여 종류 파라미터가 없어, 본문 키워드(`유족급여`·`장해등급` 등)로 요양급여 건만 후처리 필터링했다(`is_yoyang`).
- **CORS/키 보안** — 브라우저에서 공공API 직접 호출이 불가해, 서버가 키를 들고 프록시 역할을 하며 응답을 가공해 전달한다.
- **본문 추출** — 판정서 본문이 [주문/청구취지/신청내용] 정형 양식이라 정규식 휴리스틱으로 부위·직종·노출기간을 추출한다. 추출 실패 필드는 오추출 대신 공란 처리한다.

```bash

# 윈도우 CMD

```

- Python 3 필요. 외부 라이브러리 설치 불필요.
- 판정서는 실시간 조회하므로 서비스키 없이 실행하면 트리가 표시되지 않는다.
- 서비스키 발급: [공공데이터포털](https://www.data.go.kr/data/15110836/openapi.do)

## 검증

판정서는 대외비 성격이라 실무자의 직접 정량 평가가 제한된다. 대신 두 가지 방법으로 검증했다.

### 분류 정확도 — 1,253건 실측

판정서의 신청내용 서술만 입력해 별표3 질병분류를 맞히는지 측정했다. 판정 이유는 입력하지 않는다(실사용 조건과 동일).

| 질병군 | 표본 | Top-3 | Top-1 |
|---|---|---|---|
| 근골격(비척추) | 200 | **98%** | 66% |
| 근골격(척추) | 200 | **88%** | 88% |
| 호흡기 | 200 | **86%** | 79% |
| 난청 | 142 | **89%** | 70% |
| 뇌혈관 | 200 | 74% | 60% |
| 직업성 암 | 200 | 62% | 27% |
| 간질환 | 111 | 36% | 22% |
| **전체** | **1,253** | **79%** | **61%** |

주요 질병군(근골격·호흡기·난청)은 Top-3 86~98%이나, 직업성 암(62%)과 간질환(36%)은 낮다. 혼동행렬을 보면 암→호흡기(82건), 간→뇌혈관(41건)으로 혼동되는 패턴이 명확하다 — 진술에 섞인 "폐·과로" 키워드가 우선 매칭되는 규칙기반의 한계다. 이는 의미 유사도 기반 검색(STEP 1)의 정량적 근거가 된다.

### Known-item Retrieval

실제 판정서를 정답으로 숨기고 핵심 요소(부위·부담요인·직종)만으로 검색해 원본이 상위에 오는지 측정한다. 지표는 Hit@1/3/10과 MRR. 재실행 가능.

```bash
python3 verify_known_item.py "발급받은_서비스키"
# → 검증결과_요약.txt · 검증기록_사례별.csv
```

## 한계

- 분류·유사도가 규칙기반이라 동의어·표현 차이에 약하다 → STEP 1(임베딩)에서 개선 예정.
- 본문 추출이 휴리스틱이라 비정형 서술에 취약하다.
- 현재 데이터는 공공API에 의존한다. 폐쇄망 납품 시 데이터 소스를 내부 DB 어댑터로 교체해야 한다.

## 기술 스택

| 영역 | 기술 | 선택 이유 |
| --- | --- | --- |
| Backend | Python 3 `http.server` | 별도 웹 프레임워크 없이 폐쇄망 이식 가능성을 확인 |
| Data/API | `urllib`, `xml.etree`, 정규식 | 공공데이터 XML 조회·정규화·본문 휴리스틱 추출 |

| Evaluation | Python, CSV | 1,253건 Top-k 분류와 Known-item Retrieval 재실행 |
| Deployment | Render | 외부 평가자가 설치 없이 사용자 흐름을 확인하는 데모 제공 |
